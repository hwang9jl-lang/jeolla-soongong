# jeolla-soongong

**인수인계 시작:** [소스 검증·운영 인수인계 패키지](handoff/README.md) · [검증 결과](handoff/VERIFICATION.md) · [배포/복구 절차](handoff/OPERATIONS.md)

전라고등학교 순공 프로그램. HTML과 Firebase Realtime Database를 사용하는 정적 웹사이트입니다.

## 공부 기록 규칙

- 하루 기록 경로는 `records/YYYY-MM-DD/학번`입니다. 세션의 시작 날짜(KST)에 정지·재개·종료를 저장합니다.
- 시작/정지/재개/종료는 기록 단위 트랜잭션으로 처리합니다. 같은 시작 기록은 한 번만 종료할 수 있습니다. 정상 종료 후 같은 날 다시 시작하는 것은 가능합니다.
- 인정 시간은 KST 07:00 이상 22:00 미만입니다. 시작 날짜의 22:00 이후 미종료 세션은 **그날 전체 무효**입니다. 이전 날짜의 정상 기록에는 영향이 없습니다.
- `done`은 `durationSec`, `ongoing`/`paused`는 이미 완료한 `prevSec`, `invalid`는 0초를 합계에 반영합니다. 현재 진행 중인 시간은 좌석 화면의 '오늘 순공'에 표시하고, 랭킹에는 정상 종료 후 반영합니다.
- 누적·주간 합계는 기록에서 계산합니다. 기존 `students/학번/totalSec`는 더 이상 읽기 집계나 종료 가산에 사용하지 않는 이전 버전의 캐시입니다. 기록 없이 이 필드에만 있는 시간은 새 합계에 포함되지 않습니다.
- 교사의 무효 기록 인정은 그날 전체 인정 시간을 입력하는 방식이며, 해당 날짜가 아직 `invalid`일 때만 변경됩니다.
- 관리자 메뉴/실시간/과거 기록/기록·랭킹 화면에서 미종료 기록을 정리합니다. 화면이 실행 중이면 15초마다 마감을 검사하고 다시 열 때도 정리합니다. 서버 예약 작업은 아니므로 모든 화면이 닫혔거나 브라우저가 정지된 동안 정확히 22시에 DB가 바뀌는 것은 보장하지 않습니다. 늦은 종료·재개 시에도 마감을 검사합니다.

## 검증

Node.js로 네트워크 없이 실행하는 43개 동작 시험:

```sh
node tests/records.test.cjs
```

Playwright와 Chromium이 설치된 환경에서 실행하는 브라우저 시험:

```sh
node tests/browser-smoke.cjs
```

필요하면 `CHROMIUM_PATH`로 브라우저 경로를 지정합니다. 브라우저 시험의 모든 요청은 로컬 소스/가상 DB로 대체되어 실제 Firebase에 접근하지 않습니다. 15개 페이지 로딩, 로그인/공부/휴식/종료, 저장 실패와 재시도를 확인합니다. Firebase 자체의 권한 규칙이나 실제 서버 트랜잭션을 검증하는 시험은 아닙니다.

## 이번 수정 범위와 배포 전 확인

사용자 점검 번호 1, 2, 5, 6, 7, 9, 10, 11, 14, 15, 16을 수정했습니다. 3, 4, 8, 12, 13은 별도의 변경 대상으로 남겨 두었습니다.

- 사용자가 제공한 기존 규칙에 `active`와 `rosters`를 추가한 전체 교체본은 `database.rules.json`에 있습니다. 에이전트가 운영 Firebase에 직접 게시하지는 않았으며, 사용자의 콘솔 게시 여부는 독립 검증하지 않았습니다. 배포 전 별도 시험 데이터에서 기록 경로의 읽기 및 트랜잭션 쓰기 권한을 확인해야 합니다. 새 인증 방식/보안 규칙은 적용하지 않았습니다. 학생의 `active` 필드, `rosters/YYYY-MM-DD` 읽기·쓰기 및 학생 변경과 명단 저장의 다중 경로 업데이트 권한을 확인해야 합니다. 신청 경로 `applications/학번`의 트랜잭션 권한도 확인해야 합니다. 저장 권한이 없으면 명단 변경 전체가 실패하며 오류를 표시합니다.
- 새 버전 전체를 함께 배포하고, 열려 있던 학생/관리자 화면을 새로고침하여 이전 합계 계산 코드가 섞이지 않도록 합니다.
- 에이전트는 운영 DB와 기존 캐시 값을 직접 변경하지 않았습니다. 사용자는 웹 ZIP을 배포하고 테스트했다고 보고했으며, 최신 ZIP의 현재 운영 반영 여부는 독립 검증하지 않았습니다. 합계는 남아 있는 기록을 기준으로 표시되므로, 이전 중복 가산이 있던 캐시와 숫자가 달라질 수 있습니다.
- 서버 함수에서 최종 시간을 검증하는 기능, 관리자 인증, 좌석 배열 통일, 좌석/코드 생성의 동시성 처리는 이번 범위 밖입니다.

## 11번: 중복 신청 방지

같은 학번의 최초 신청만 트랜잭션으로 저장합니다. 중복 신청 또는 재시도 시 기존 이름·순번·처리 상태를 그대로 반환합니다. 동시 요청/저장 실패로 예약 순번에 빈 번호가 생길 수 있지만, 선발은 실제 신청 목록을 정렬한 앞 60명을 기준으로 하므로 빈 번호 때문에 정원이 줄지 않습니다. 학생의 잘못된 학번 입력 자체를 본인 인증하는 기능은 아닙니다.

## 14번: 과거 참여자와 명단 보존

- 신청 관리에서 명단을 다시 확정할 때 제외된 학생은 삭제하지 않고 `active: false`로 보존하고 현재 좌석만 해제합니다. PIN과 공부 기록은 유지합니다. 다시 확정하면 활성화되며 좌석은 새로 배정합니다.
- `active` 필드가 없는 기존 학생은 현재 참여자로 취급합니다. 비활성 학생은 현재 배정·인쇄 좌석표·실시간 현황·학생 랭킹에서 제외됩니다.
- 기록·랭킹 화면의 **과거 참여자 포함**을 선택하면 비활성 학생도 표시하며, CSV에도 같은 선택이 적용됩니다. 옛 버전에서 학생이 삭제됐더라도 공부 기록이 남아 있으면 과거 참여자로 조회할 수 있습니다.
- 관리자 메뉴 또는 과거 기록 화면을 열 때 오늘의 초기 명단을 저장합니다. 이후 참여자 확정/좌석 변경과 `rosters/YYYY-MM-DD` 저장은 원자적인 다중 경로 업데이트로 처리합니다. 명단에는 학번·이름·반·좌석만 저장하고 PIN은 넣지 않습니다.
- 날짜별 스냅샷은 해당 날짜의 마지막 명단/좌석 배정입니다. 명단 변경이 없는 날짜는 그 이전의 가장 최근 스냅샷을 이어 씁니다. 공부 기록이 있으면 기록에 저장된 당시 이름·좌석을 우선하며, 같은 자리에 여러 학생의 기록이 있으면 모두 표시합니다.
- 최초 스냅샷보다 이전 날짜에는 현재 명단으로 결석자를 추정하지 않습니다. 기록이 있는 학생만 표시하고 결석 인원은 **확인 불가**로 표시합니다. 과거 결석자·배정 이력을 새로 복원하려면 별도의 당시 자료가 필요합니다.
- 모든 학생/좌석 변경은 새 버전 화면을 통해 처리해야 명단 이력이 함께 남습니다. Firebase 콘솔 직접 수정이나 이전 버전 화면의 변경은 이력에 자동 반영되지 않습니다.
- 전체 초기화는 과거 명단(`rosters`)도 삭제합니다. 기록만 초기화할 때는 명단 이력을 유지합니다.

## 7번: 서버 시각 보정

- Firebase `.info/serverTimeOffset`와 `.info/connected`를 구독합니다. 서버 연결과 유효한 시각 보정값이 확인된 뒤 페이지의 조회·자동 처리·입력 기능을 시작합니다. 최초 확인이 지연되면 연결 확인/새로고침 안내를 표시합니다.
- 서버 시각으로 맞춘 기준점에서 `performance.now()`의 경과 시간을 더합니다. 기기 시계 조정만으로 타이머가 갑자기 늘거나 줄지 않습니다.
- 시작·정지·재개·종료 및 마감 정리는 연결 상태를 확인합니다. 기기 시계와 단조 시계의 경과 차이가 5초를 넘으면 절전 복귀/시각 변경으로 판단해 Firebase를 재연결하고 해당 저장은 재시도하도록 안내합니다.
- 연결이 끊기면 타이머는 마지막 서버 기준점으로 계속 표시하지만 새 저장 작업은 차단합니다. 사용자는 다시 연결된 뒤 버튼을 눌러야 합니다. 이미 서버로 전송된 요청의 취소까지 보장하지는 않습니다.
- 오늘 날짜, 07시/22시 판단, 타이머 계산, 관리자 시간 표시를 보정 시각과 KST 기준으로 통일했습니다. 미국 시간대에서도 같은 한국 날짜와 시간으로 동작하도록 검증했습니다.
- Firebase의 시각 보정값은 네트워크 지연 영향을 받는 추정치입니다. 이 변경은 클라이언트 시계 오류 보정이며, 서버 함수/보안 규칙에서 최종 공부 시간을 강제 검증하는 기능은 아닙니다.
- 페이지별 실행 코드는 `application/x-soongong` 스크립트로 보관하고 서버 시각 확인 후 실행합니다. HTML과 공통 JS를 함께 배포해야 합니다.

## Firebase 규칙 적용

1. Firebase 콘솔에서 `jeolla-soongong` 프로젝트의 Realtime Database → 규칙을 엽니다. 기존 규칙을 별도로 복사해 보관합니다.
2. `database.rules.json` 파일 전체를 복사하여 편집기 내용을 교체합니다. 파일에는 실제 JSON만 들어 있으며 메시지에 있던 `\`와 HTML 공백 표기는 제거했습니다.
3. 콘솔에서 규칙 오류 여부를 확인하고 게시합니다. `firebase.json`에도 이 파일을 등록했지만, 파일을 소스에 저장하는 것만으로 운영 규칙이 게시되지는 않습니다.
4. 테스트 학생으로 신청, 확정, 좌석 배정, 시작/정지/재개/종료, 비활성화 및 과거 명단 조회를 확인합니다.

기존 규칙과 달라진 것은 학생의 Boolean `active` 허용과 날짜별 `rosters` 허용입니다. 명단 스냅샷에는 이름·학번·반·좌석만 허용하고 PIN 등 추가 필드는 거부합니다. 빈 명단, 좌석 해제, 전체 초기화를 위한 삭제도 허용합니다. 기존 공개 읽기/쓰기 정책은 그대로이므로 관리자 인증을 대신하는 보안 강화는 아닙니다.

검증 범위: JSON 구문/필드 구조와 파일 연결 확인, 애플리케이션 가상 DB 시험 43개 통과. Firebase Emulator 또는 운영 Firebase에서의 규칙 컴파일·권한 시험은 아직 수행하지 않았습니다. 현재 환경에는 Firebase 배포용 관리자 인증이 연결되어 있지 않습니다.

### 일시정지 시 새로고침 요구 수정

시작/재개 트랜잭션의 반환 스냅샷에 남을 수 있는 서버 시각 추정값을 다음 상태 비교에 사용하지 않도록, 저장 후 서버 기록을 다시 읽습니다. 임시 시각과 확정 시각이 37ms 다른 상황에서 새로고침 없이 시작→정지→재개→정지→종료하는 회귀 시험 및 브라우저 시험을 통과했습니다. 실제 다른 세션/상태 변경과 중복 종료는 계속 차단합니다. Firebase 규칙 변경은 필요하지 않습니다.
