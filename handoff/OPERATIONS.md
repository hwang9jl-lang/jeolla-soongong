# 배포와 운영 인수인계

## 배포

1. `python3 scripts/package_release.py`로 배포 ZIP과 인수인계 ZIP을 생성합니다.
2. `artifacts/manifest.json`의 각 파일 SHA-256과 deploymentSha256을 보관합니다. workingTreeDirty=true면 커밋 번호만으로 소스를 식별하지 말고 파일 해시도 확인합니다.
3. Cloudflare Pages의 **기존** jeolla-soongong 프로젝트에 `soongong-deploy.zip`을 프로덕션 직접 업로드합니다. ZIP 최상위에 index.html이 있고 웹 파일은 22개입니다.
4. Firebase 규칙을 바꾼 버전이라면 Firebase 콘솔 Realtime Database → 규칙에 `database.rules.json` 전체를 별도로 게시합니다. GitHub 푸시나 웹 ZIP 업로드만으로 규칙이 바뀌지 않습니다.
5. 학생·관리자 화면을 닫고 다시 열거나 새로고침합니다. 테스트 학생으로 실제 저장을 확인한 뒤 운영합니다.

최신 준비 ZIP은 2026-11-04 15:04:30 KST 버전이며 일시정지 수정과 신청 상태 표시를 모두 포함합니다. 이 날짜는 파일 준비 시각이지 Cloudflare 게시 완료 시각이 아닙니다. 소스와 ZIP의 일치는 evidence/source-manifest.json에 기록했습니다.

## 복구와 백업

Cloudflare 배포 이력에서 이전 버전으로 복구하거나, 보관한 이전 배포 ZIP을 사용합니다. 이전 버전은 새 active/rosters 의미와 집계 방식이 다를 수 있으므로 복구 후 새 기록·명단 변경을 하기 전에 호환성을 확인해야 합니다.

저장소 최초 커밋 028230a는 작업 전 소스입니다. 당시 실제 운영본과 일치 여부는 검증하지 않았습니다. 소스 ZIP은 Firebase 데이터 백업이 아닙니다. 학생·기록 백업은 Firebase 콘솔에서 별도로 내보내고, 개인정보가 포함되므로 저장소에 커밋하지 않습니다.

## 신청과 탈락

신청 목록은 이력입니다. 자리 배정이나 공부 시작 후에도 남습니다. '참여 확정 · 배정 좌석'과 '확정후보 · 아직 미확정'으로 구분합니다. 상단 확정후보는 탈락자를 제외한 상위 60명의 후보 수이며 현재 공부 중인 인원과 다릅니다.

탈락은 두 단계입니다.

1. 신청 관리에서 탈락 처리: 신청 상태만 rejected로 변경됩니다.
2. '확정 명단으로 자리 배정하기': 전체 후보 명단을 다시 반영하며 제외된 학생은 비활성화되고 자리가 해제됩니다.

테스트로 탈락시켰다면 되살리기를 사용합니다. 실제 참여를 끝낼 학생이 공부 중이면 먼저 순공 종료로 기록을 저장한 뒤 명단에서 제외하는 편이 좋습니다. 과거 기록은 계속 보존됩니다.

## 현장 문의 대응

| 상황 | 설명/확인 |
|---|---|
| 신청자 목록에서 사라지지 않음 | 정상 이력 보존. 실시간 현황에서 공부 상태 확인 |
| 탈락시켰는데 자리/랭킹에 남음 | 명단 재확정 전인지 확인. 탈락 버튼만으로 비활성화하지 않음 |
| 과거 기록에 탈락 학생이 남음 | 정상. 이전 출석을 보존 |
| 비행기 모드인데 타이머가 흐름 | 정상. 연결 후 저장 버튼을 다시 누름. 일시정지 저장이 성공했는데 시간이 흐르면 오류 |
| 일시정지에서 다른 화면 변경 안내 | 최신 수정본 여부 확인. 다른 탭의 실제 조작도 확인. 해결 안 되면 시각/상태/메시지를 수집 |
| 서버 시각 확인 중 | Firebase 연결/CDN 로딩 확인. 시각 준비 전 기능 실행을 막는 상태 |
| 권한 없음 | active/rosters 규칙 게시 여부, 경로 권한 확인. 화면상 임시 표시만 보고 저장 성공으로 판단하지 않음 |
| 그날 기록 전체 무효 | 미종료 상태로 22시를 넘겼는지 확인. 필요하면 교사가 그날 전체 인정 시간을 분 단위로 입력 |

장애 보고에는 발생 시각(KST), 기기/브라우저, 페이지, 수행 순서, 오류 문구, 연결 상태, 다른 탭 사용 여부를 기록합니다. 실제 PIN이나 전체 학생 데이터는 채팅/이슈에 올리지 않습니다.
